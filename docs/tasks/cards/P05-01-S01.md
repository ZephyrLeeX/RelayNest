## 本任务工作

1. 提供供 Bot、消息及后续 P06 共用的最小全局日志追加能力：接受调用方 `*sql.Tx`，在该事务中插入现有 `changes`，返回准确的 SQLite 分配序号并传播错误。不另开事务/连接、不提交/回滚调用方事务，不触发网络、广播或业务命令。调用方业务写入、版本更新和事件必须共同提交；返回序号不等于事务已提交。
2. 精确复用字段：`change_seq INTEGER PRIMARY KEY AUTOINCREMENT`；`type`/`entity_id` 非空文本；`revision INTEGER >= 1`；可空 `bot_id`；非空 `created_at`。不添加 FK、payload 或历史正文列。时间沿公共 UTC RFC3339 Z 契约；实体版本和 ID 由调用方业务拥有，本基础不生成 Bot/version、不进行授权或 CAS。明确参数/错误及空值表示，保证无静默截断或版本与事件序号混用。
3. 以冻结字面值建立最小共用事件类型映射；日志元数据与线缆投影分开，不能将数据库行直接当作完整 `SyncChange` JSON。必需的线缆序列化只覆盖本基础持有的全局序列/事件类型，完整投影由后续同步实现读取当前实体后组装：

| 事件 type | 冻结 SyncChange 除 type/change_seq 外的键 |
| --- | --- |
| `message.upsert` | `message` |
| `message.deleted` | `id`, `bot_id`, `bot_seq`, `revision`, `deleted_at` |
| `bot.upsert` | `bot` |
| `bot.deleted` | `id`, `version`, `deleted_at` |
| `read.updated` | `read` |
| `delivery.upsert` | `delivery` |
| `device.notifications.updated` | `settings` |
| `settings.updated` | `settings_version`, `recovery_path`（固定 `/admin/settings`） |

4. 全局 `change_seq` 与每 Bot 的 `bot_seq`、共享 `read_seq`、投递/路由序列、实体 `revision`/`version` 分离。线缆 `Sequence` 是 0～9223372036854775807 的规范十进制 JSON 字符串，不能转 float 或 JSON number；实际追加序号从正数开始。公共 `Version`/revision 仍为从 1 起的 JSON integer，不借本卡改为字符串、不擅加全局 2^53−1 上限；特定资源的独有上限由各自冻结契约处理。
5. 提供按调用方事务读取已持久化 `system_state(id=1).sync_epoch` 的能力。epoch 生成/首次持久化归既有 0001 迁移和启动路径；本模块只读，不生成/重置。空日志不创建假事件，epoch 在同一数据库关闭重开后稳定；更换数据库才有另一初始化 epoch。读状态缺失/损坏时显式失败，不自动修库或旋转 epoch。
6. 维持 SQLite AUTOINCREMENT 已提交序号单调、不因删除日志回退；不承诺连续、无空洞或回滚产生的未提交序号永不复用。达到 SQLite 有符号 64 位上限后追加失败，不 wrap、不复用旧已提交序号、不重置 epoch/序列/表。并发顺序交给现有 SQLite 写事务约束；不能依赖进程内计数器或预取序号。

具体 Go 导出函数/类型签名及错误约定由本卡实现、独审与集成的真实结果交接，不把规划名称当作已冻结接口。报告必须说明 Bot 同事务调用方式和返回值何时可对外承诺；未来 P05/P06 复用同一集成结果，不复制私有追加实现。

## 明确不做

- 不实现消息 CRUD、bot_seq 分配、Bot CRUD/凭据/CAS、投递/push 调度或业务权限。
- 不实现 HTTP、WebSocket、鉴权、同步分页/游标/高水位、bootstrap、当前实体投影或完整 SyncChange 响应组装。
- 不决定删除墓碑载荷保留、日志清理/floor、历史补写/迁移、恢复策略；不为填未知投影字段持久化 payload 或旧正文。现有 changes 无 Bot FK，保持删除后可追赶的既定边界。
- 不修改产品/信任边界、公共 API/设计或 RelayShelf，不执行命令/MCP 工具，不派生 agent、不改台账、不 push。

## 测试与完成标准

- [ ] 真实 SQLite 调用方事务同时写测试实体、更新版本并追加事件：提交后三者一致可见；追加失败或调用方在追加后返回错误时全部回滚；本基础不提前提交。用测试专用表证明边界，不实现 Bot/消息桩业务。
- [ ] 初始日志无事件；成功追加返回实际正整数序号，与行值一致；混合实体/事件共享一个全局递增序列，关闭重开及删除日志后继续递增。
- [ ] 多个独立 Store/连接访问同一文件并发追加，成功提交的事件无重号；不得只测单 Store 写池。若遇锁等待/上下文失败，准确传播、无半写，不弱化现有 WAL/锁约束。
- [ ] 首次初始化 epoch 合法且可读，空库及多次关闭重开/失败事务后仍一致；缺失状态显式错误，不发生隐式重建。
- [ ] 按八种冻结字面值核对映射与投影键边界；本基础不输出伪造完整 SyncChange。全局 Sequence 的 0、1、2^53 前后、int64 最大值均精确输出 JSON 字符串；负值、溢出入口不得截断/绕回，公共 revision 仍为整数。
- [ ] 真实 SQLite 接近/达到最大 change_seq 的测试：末值可提交，之后失败且调用方业务写入回滚；epoch 不变、旧已提交行不覆盖。不得在生产路径修改 sqlite_sequence；测试专用库可构造边界。
- [ ] 在 `server` 执行 `go test ./internal/changes ./internal/storage`、`go test -race ./internal/changes`、`go vet ./internal/changes ./internal/storage` 及 gofmt 检查，逐项记录环境/结果；必需检查未运行则保留 blocked，不伪称通过。
- [ ] 仅提交本卡精确允许路径；交付基线/实现 SHA、调用方事务与错误交接、检查证据/限制。独立审计精确实现 SHA 并集成后才可 done，供 Bot 和父卡消费。
