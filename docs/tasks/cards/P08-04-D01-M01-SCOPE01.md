M01 实施补充允许 `server/internal/storage/offline.go`，候选内部 Go 签名 `OpenOffline(ctx context.Context, cfg Config) (*Store, error)`。它在现存文件 `mode=rw` 下构造原 Store，严格校验全部当前嵌入迁移的连续版本/name/checksum及完成数量，严格读取已提交身份；缺 ledger/未完成/未知版本/损坏拒绝。不得调用 `migrate`、Init 或 `enableWAL`，不得 CREATE/ALTER/补台账/新建库；不改原 Open 或公开网络契约，不对任意未来迁移编号硬编码。

使用现有私有连接池字段和事务机制，正常关闭所有已打开连接；离线连接保持 foreign_keys、synchronous 和写事务锁约束。迁移核查只读，SQLite 的常规 WAL/SHM 行为不等于许可改 journal 模式或执行 schema 迁移。身份/代次/全部会话及现有推送映射仍只在一次 Store.Write 内修改；候选新 ID 不得先发布。

## 并发、安全与失败边界

维护入口对实际 DB inode 获取非阻塞排他 flock，保持到事务结束和 Store 关闭；同机路径别名不能绕过锁。本版 HTTP 主进程在打开/迁移库前取得同 inode shared flock，持续到请求排空、Store 关闭后释放；拒绝维护期间服务启动。首次正常启动建库仍只由正常启动路径承担。辅助锁可留在独立维护入口供 main 复用，不扩展 storage.Open 的生命周期。

这是已批准“排他操作/运行进程失败安全退出”的局部协调实现，不证明旧版本、既有 admin 工具、其他机器或不遵守 flock 的进程已停止；SQLite 写锁也不证明停服。`--confirm-offline` 所承诺的停全部进程并隔离入口仍是必需人工前置。不得在本卡引入在线换 ID、全系统锁服务或自动停服；若要把锁提升为自动证明所有写者停机，须另报安全/架构决定。

冻结退出码严格保持：0 已提交；2 用法/确认错误；3 DB busy/排他锁不可用；4 身份缺失/腐败/expected 不匹配/迁移未完成；1 其他存储/随机/撤销/提交错误。不能因 SQL 错误包装了身份 sentinel 就把随机/写入/提交错误全部归为4；内部保留错误原因，外部仅固定脱敏文本。提交成功后关闭/输出失败不能宣称事务回滚；测试须区分提交结果与报告错误，不能增加未冻结的退出码。
