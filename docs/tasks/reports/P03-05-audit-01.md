## 编号发现

### P03-05-A01-F01 — P2：尾部换行绕过 Content-Range 格式及区间关系校验

- **位置**：`server/api/validate.py:39–46`；`server/api/openapi.yaml:1747–1752`，以及 downloadAttachment 的 206/416 Content-Range 响应头模式。
- **触发**：`ContentRange` 及具体 206 响应头均接受 `"bytes 9-0/1\n"`；具体 416 响应头接受 `"bytes */100\n"`。Schema 中 `$` 可在字符串最终换行前匹配，而自定义 `content_range` 使用 `fullmatch`，遇到不匹配只结束、不产生错误。因此换行同时使格式检查误过和数字关系检查不执行，逆区间也变成合法结果。
- **实际证据**：直接调用固定实现的 `ContractValidator(...).is_valid(...)` 返回 `True`。另外在仓库外临时目录载入原契约与全部原示例，追加上述两项且故意标记 `valid: true`，分别绑定 `downloadAttachment` 的 206/416 `Content-Range`；执行原 `main()` 仍输出 `PASS: OpenAPI 3.1; 44 schemas; 94 valid + 127 invalid examples; 18 operations/security`。该 94 正例数字仅用于展示漏洞，仓库原套件仍为 92/127，没有修改原示例。
- **影响**：当前契约校验会认可带非法换行的响应头和违反 `start <= end < size` 的 206 区间，无法作为宣称的 Content-Range 边界回归门槛。当前没有运行时附件服务，本发现不声称实际服务存在响应头注入或权限漏洞。
- **修复方向**：让 ContentRange 及具体响应模式拒绝 CR/LF；自定义扩展完整识别合法单区间和 `*/size` 两类，其他值显式返回 ValidationError，不能以解析失败跳过语义检查。添加 Schema 与具体 206/416 响应头层面的回归反例。
- **复验**：`bytes 9-0/1\n`、`bytes 0-1/100\n`、`bytes */100\n` 以及 CR/CRLF 变体均应拒绝；保留合法 206 单区间、416 `*/size`，原 219 示例、Range 矩阵及 OpenAPI 检查继续通过。
