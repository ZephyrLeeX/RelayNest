## 发现

### DS-A01-01 / P1：device_id 不能在现有契约下唯一确定待撤销的有效会话

**证据**：`server/api/openapi.yaml:159` 列出有效会话，明确 Session.id 每登录新建；`:209`～`:210` 把路径 id 定义为 Session.device_id，再声称事务定位该设备“当前有效 Session.id”，只撤销所选代次。既有 login 描述 `:113`～`:116`、LoginRequest 的 device_id 定义及 Session `:2095`～`:2124` 没有约束同设备仅一个有效会话，也没有重新登录替换/撤销旧会话或多个有效会话的选择规则。T7.1定义空闲/绝对期限与单端重登，未补该基数约束；T3.2设备路由表要求撤销指定会话，父验收1和子卡要求完整设备会话撤销事务。

**触发与影响**：同一安装使用相同 device_id 连续两次登录，新建 S1、S2；S1 尚未到期且未退出。冻结输入不禁止二者同时有效。列表可以出现两个同 device_id、不同 Session.id 的记录，两行对应的 DELETE URL 完全相同，调用方不能表达所选会话。服务端也没有确定的“当前”选择依据；只撤销一个可能遗留另一个有效凭据/provider/WS。并发登录与撤销时，未定义旧会话何时失效及代次切换线性化边界。已有“操作只作用事务所选代次”和“不承诺跨重登重试幂等”能约束选中之后的迟到操作，但不能解决选择之前的基数歧义。

**独立复现**：从新增合法“设备会话列表”夹具取第一条 Session，复制一条、保持 device_id 不变、仅把 id 改为另一个合法 ID（`22222222-2222-4222-8222-222222222222`）；组合成两个 items。当前 ContractValidator + FormatChecker 接受该 DeviceSessionPage。此结果只证明现有结构允许此状态；缺陷依据还包括上述登录与撤销声明均未定义排除此状态的不变量，不能仅靠 Schema 的 uniqueItems 修复。现有 device_session_state 只有单个 session_id，未建模同 device_id 两个有效会话或登录/撤销交错，故676例通过未覆盖此处。

**最小修复方向**：先由总调度按项目重要安全/外部接口变更规则取得明确决定，不能在审计中默认批准单活。可选方向为：保留 device_id 路由并明确每设备有效会话的基数与确定选择/失效规则；若选择每设备单活，须定义重新登录原子替换旧代次及其 provider/WS、并发登录/撤销先后语义；若保留多活，则需批准可定位目标会话的契约或明确设备级全部会话撤销语义。后两种若改变本卡已固定的“指定单代次”范围/路径，也须重新确认。不能直接将路径 id 偷换成 Session.id。

**影响及复验**：修复至少涉及本子卡设备事务及合成例/声明校验；若采用单活，应显式补充冻结 auth/login 生命周期语义，重开相应认证契约范围并对受影响操作、Session、WS撤销关联重新独立审计，不能默默突破本轮旧操作等值冻结。补同 device_id 连续登录、并发登录、撤销在登录前/后线性化、旧回调/迟到撤销结果不复活也不覆盖新代次的正反声明及破坏探针；重新比较经批准的冻结差异，并重跑 OpenAPI/validate。无需借机定义注册/通知资源或更改同步/bootstrap。
