## 发现

### BS-A01-01（P2）：初始游标也能充当最终追赶完成游标

**证据**：`server/api/openapi.yaml:1476` 将 bootstrap 返回的初始 `sync_cursor` 定义为 `completed-cycle-at-H-same-administrator-and-epoch`；`:1477` 的最终门槛是完成轮次且位置至少 H。`server/api/README.md:138` 同时要求客户端先调用 sync 追赶，再携追赶完成游标 verify。`server/api/validate.py:170–184` 的 verify 声明实现仅检查合法性、管理员、epoch、`cycle_complete` 和 `position >= H`，不能区分原始种子游标和实际 sync 返回的完成游标。

**触发与影响**：固定 H=10，分页期间新建 change_seq=11 的消息；该消息按创建边界不会进入 bootstrap 页。客户端取得合法末页 receipt 后，直接将 bootstrap 初始位置10、完成标记为真的游标提交 verify，省略 `(10,current]` 追赶。当前定义仍满足成功条件，而“全页→追赶→再检→切换”中追赶实际未发生。这使新增加的 verified 门槛不能支持其“追赶完成后切换”的含义；不能据该成功响应判定新 generation 已补齐期间增量。遵守 README 主动完成 sync 的客户端不由此必然出错，本发现不是已运行 HTTP 或 Android 的数据丢失结论。

**独立复验**：加载被审 validator，取现有成功 verify 声明，将 `position` 改为该声明的 `h`（10），保持同身份/epoch、合法 receipt、`all_pages_complete=true`、`cycle_complete=true`、预期200；`bootstrap_state_valid` 返回 `True`。这些属性正是初始游标的冻结定义；测试没有引入伪造签名或跨身份假设。现有 verify 反例覆盖未完成轮次及位置小于H，却没有初始种子游标直接复核的反例。

**修复方向**：在本卡新增 bootstrap 契约内明确区分“供 sync 开始追赶的种子”与“真正执行 sync 后产生的完成证明”，使 verify 不能把前者当成后者。保留已冻结 sync 行为；如实现方案必须改动旧接口，先交调度确认范围。不能只把 `>=H` 改成 `>H`，因为无新事件时合法追赶仍可能完成于H。同步更新说明、声明检查和示例。

**修复后必要复验**：H=10/current=11 时直接用初始游标被拒绝；实际追赶至11后成功；current=H时实际零变化 sync 完成后仍可成功；实际 sync 未完成、跨身份、epoch错误、过期、floor>H均按既定错误拒绝，floor=H仍可继续。复跑全部旧操作/组件/示例/两锁比较及本卡检查。
