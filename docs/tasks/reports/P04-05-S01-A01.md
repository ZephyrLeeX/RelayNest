## F01：续期接受来自另一安全入口/会话库的身份对象（P2）

定位：`server/internal/auth/request_security.go:24–28,49–51,90`。

`AdminRequest` 私有部分只保存 SessionSecrets，没有签发者或 store 绑定；`RenewRead` 只把私有 token 和公开可变 ClientType 交给接收者自己的 SessionStore.Authenticate，不核对签发 guard/store 或原 Session.ID。因此将 A 检查得到的 actor 误交给 B 时，只要 B 库也存在同凭据，B 会成功续期并返回 B 的身份，即使 A 的该 actor 已被撤销且两边 Session.ID 不同。没有同凭据时会拒绝，但不能据此保证跨 store 身份对象不可误用。

独立复现使用两个真实 SQLite HTTP 夹具和 Go overlay，未改工作树源码。步骤：两库正常初始化；仅将两个 SessionStore 的测试随机源设为 48 字节（头 16 字节产生不同 Session.ID，尾 32 字节相同以模拟分叉库共享凭据）；分别 Create Android 会话；A.Authorize 获取 actor；A.Revoke；推进 B 时钟一小时；B.RenewRead(A actor)。断言应拒绝，实际返回 nil error、不同 Session.ID，并改变 B 的 idle_expires_at。token 不打印。输出：

```text
=== RUN   TestAuditForeignGuardRenewal
foreign actor accepted: same identity=false; target store changed=true; source revoked=true
--- FAIL: TestAuditForeignGuardRenewal
FAIL relaynest/server/internal/auth
```

该夹具刻意构造共享凭据，不声称生产随机碰撞、当前单 store HTTP 可被远程绕过或已有跨实例路由。问题是新增公共安全接口不能可靠拒绝错误接线，消费者可能先按 A 的身份执行读取、再由 B 续期验证出另一身份，构成权限/有效性错配；这也是本次派发要求检查的跨 security/store 边界。

最小修复方向：在 Authorize 返回的私有状态绑定签发者/会话库与原身份，RenewRead 访问数据库前拒绝不匹配对象，避免依赖公开可变 Session 字段作为可信输入；补充不同 guard/store、零值/篡改快照、原库撤销后跨库复用的拒绝测试，并验证拒绝无续期。具体绑定相同 store 下多个 guard 的策略应明示；不得因此增添另一套 HTTP 安全规则。审计不自修，需修复提交后固定 SHA 重审。

## 消费者边界与遗留

F01 修复及重审前不放行 S01 供后续消费者派发。公共入口仅证明请求检查时有效；`RenewRead(ctx,actor)` 必须检查错误后响应，不能作为业务写事务授权。自撤成功后才 ClearCookie，失败统一 WriteSessionError；不得将 Session.ID 当 device_id。

实施报告对事务限制的说明真实：当前 SessionStore 的 Inspect/Authenticate/Revoke 均内部自行 Store.Write，没有公开接收现有 sql.Tx 的 actor 复核方法；现有 Bot Repository.Create/Patch 签名无管理员 actor，各开自己的 Store.Write。因此 S01 通过也不能直接将 Bot 标记 ready，不能以“先 Authorize/RenewRead，再调用现有 Create/Patch”满足提交前授权。P04-05-S02 必须实际补足同一事务内 actor/target 的精确 Session.ID、归属、撤销、期限、管理员代次复核和成功续期，补竞争/重置/撤销证据；Bot 管理消费卡仍需补自身事务接入，不得仅依赖 S01 请求入口。本审计未实现或验收设备/Bot HTTP、事务组合、真实 WS 失效或外部设备。
