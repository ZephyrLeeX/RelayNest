## 审查结论与实施交接约束

未发现阻止用户选择的缺陷。提案17–37行把例外限制在两附件操作：通道格式检查后只允许提前做 Bot API 识别；无附件流/Range/资源读取、无 Admin 会话认证；确认不是匹配 API 凭据才进入 Android 的 ID→Admin 顺序。匹配 Bot 后的禁用、能力不足、资源不授权、代次失效和依赖失败均不得回退 Admin。无效 Bot 缺头由旧401变400、错头400/409、Bot lookup 故障优先503，以及 no-store/无秘密日志/可观察状态和时序限制均已公开。

以下是获准后必须落实的狭窄实现/复验条件，不是现有代码已经满足的验收结果：

1. 现 Authenticate 不能直接完成下载身份发现，因为必须先有 botID。需要最小内部适配，区分“确定不匹配”“摘要已匹配（包含禁用拒绝）”“存储/依赖失败”；之后固定身份分支。不能通过 `err != nil` 或 ErrUnauthorized 统一触发 Admin fallback。尤其匹配后的事务代次失效即使返回401也必须终止 Bot 分支。不得用附件查询预取 botID，不得把 WebhookKey 纳入可匹配集合。
2. 认证匹配与资源授权分开：上传 bot_id 必须与已认证 Bot 及原资源域一致；receive-only 不可上传；下载不能把 send/receive 任一能力直接当作任意附件下载权。基线通用 AuthorizeTx(Download) 只检查 receive，不能冒称它单独实现 OpenAPI 的 send 下载及领取事件资源范围；后续须按冻结契约核真实附件路径，缺失路径仅记未来门禁，不扩大本轮开发范围。
3. 对缺头/畸形头/错ID分别覆盖有效、禁用、能力不足、跨Bot、Webhook、无行、错误摘要、旧凭据、查询故障/超时，以及匹配后撤销/代次变化。所有故障分支须无业务副作用、不暴露附件是否存在；DB错误不能降级为“不匹配”。日志禁止 header、token、credential_id、实例 ID、附件路径、正文，固定路由不能记录原始附件 URL；request_id 不可成为原始秘密的回显通道。
4. B01 现允许路径不含 `server/internal/bots/authorization.go`，且写明 Bot 原规则。获准 C01 后由调度明确新增的内部匹配适配路径/回归范围，或拆狭窄服务卡；不得把提案 PASS 当作修改 Bot 模块或新增路由的授权。本次无源码改动。

这些条件落实后才能检查运行时；2190合成例和20声明变异检查预设身份分支，不能证明 HTTP wire 分流闭合。

## 候选比较与最小用户决定

Bot-first 保留有效旧 Bot 的请求形态，代价是允许两操作在 ID 前读取并认证 Bot 候选，以及无效凭据/DB错误的优先级变化。停用 Bot 仍属已匹配分支，不能因“不是有效启用 Bot”转 Admin。提案说“不匹配”须按此精确定义。

显式非秘密分支标识可以在读取 Bearer 前选定 Android/Bot 通道，但必须冻结缺标识处理。强制标识会阻断旧 Bot；缺标识默认 Bot 可保留旧 Bot，却使旧 Android 走 Bot401，无法同时承诺统一缺ID400。伪称 Bot 的 Admin 值只能被 Bot 认证拒绝，不得取得管理员权限。独立路由同样可先选通道，但增加路径/调用端迁移；保留旧混合路由仍须解决原问题。两者都不能保证 HTTP 凭据字节从未抵达错误部署，不能冒充 G2。

建议向用户仅询问本次新增决定：

> 是否批准仅 uploadAttachment/downloadAttachment 使用 Bot-first：允许 ID 前只做 Bot API 匹配/认证；匹配后固定 Bot 身份，任何授权拒绝/代次失效均不回退 Admin；仅确定不匹配进入 ID→Admin；接受旧 Android及无效/过期 Bot 缺头可能401→400、错头400/409，以及 Bot lookup 故障优先503（INSTANCE_UNAVAILABLE、固定文案、retryable=true）？若不接受，选择先冻结显式标识或独立路由，并明确旧客户端处理。
