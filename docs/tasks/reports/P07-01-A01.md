## A01-F01（P1）：原生 fetch 以错误 receiver 调用，全部浏览器认证请求失败

- 文件：`web/src/auth/client.ts:15`（默认 transport 为浏览器原生 fetch）、`:23`（`this.transport(...)`）；关联 `web/src/auth/tests/browser.mjs:90`。
- 触发：生产 Web 默认创建 `new AuthClient()`。将 fetch 放在实例属性后通过成员调用，使其 receiver 成为 AuthClient，Chromium 的 Window.fetch 品牌检查抛 TypeError，尚未发出 HTTP 请求。
- 影响：初次会话恢复、错误密码、正确登录及退出均无法走到后端，只显示“网络连接失败，请检查连接后重试。”。这不是断言文案错误，也不是恢复后的字体/共享库问题。
- 独立复现：原脚本先完成真实手工 Cookie jar 检查，再于 line90 等待“用户名或密码错误”超时 30000ms，退出 1。使用 ENV01 二进制和本审计重新构建的生产二进制各执行一次，结果相同。
- 临时网络/DOM探针：页面与 JS/CSS 均 200；没有 login/session API 请求；点击后 alert 为网络失败、aria-busy=false、密码已清空。没有 pageerror，因为异常已被错误壳层捕获。
- 同一真实 Chromium 页面对照（不输出凭据）：

```js
try { await ({ transport: fetch }).transport('/api/v1/auth/session'); }
catch (e) { String(e); }
// TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation
await fetch('/api/v1/auth/session').then(r => r.status);
// 401，生产后端实际响应
```

- 因果探针：仅 `/tmp` 副本在新 page 前添加下方 preload，源码/构建产物不变，原有全部断言保留，随后真实后端浏览器分支及协议桩分支均执行通过：

```js
await context.addInitScript(() => {
  window.fetch = window.fetch.bind(window);
});
```

- 最小修复方向：默认 transport 使用绑定正确 receiver 的 fetch，或通过包装函数作为普通调用转发，保留可注入 transport 与同源/CSRF 策略；不需要改变接口或引入依赖。增加覆盖默认浏览器 transport 的回归，修复后不加 preload 跑完整原脚本。Node 单元所用 arrow transport 与 Node fetch 不能发现浏览器品牌检查差异，4/4 不能代替此回归。
