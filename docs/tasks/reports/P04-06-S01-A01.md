## 检查结论

1. 凭据：每种公开标识及秘密分别使用 crypto/rand 的 32 字节；两套独立生成，持久化仅 SHA-256 摘要，恒定时间比较。普通 Bot 投影无秘密或摘要；创建模型严格为 bot/api_token/webhook_key。只有外层 Write 成功才释放创建结果，提交失败返回零值。新增代码无凭据日志调用；未来 HTTP 仍须脱敏映射底层错误。
2. 身份与授权：Identity 绑定字段私有；Bot、种类、标识、代次不可经公开访问器篡改。零身份、其他 Bot、错误种类/代次、未知操作及管理操作均拒绝；API send/receive 独立，Webhook 仅 Send。停用覆盖认证与提交授权。
3. TOCTOU：AuthorizeTx 明确要求实际业务 Store.Write 内调用、传播错误；当前 Write 使用 SQLite immediate 写事务，重新读取当前 enabled、能力、标识和代次。独立 Store 竞争测试验证撤权事务先提交后旧身份不能追加 change。能力使用认证快照与当前值交集，符合 T7.2 能力绑定与提交前撤权要求；新增能力须重新认证，旧身份不能提升。未来 P05/P06 接入必须继续遵守同事务约束，不能把本次测试当作未来路由已集成证明。
4. 版本与原子性：Bot.version 为正 int64，PATCH 在写事务内比较版本并执行带版本条件的 UPDATE；达到 MaxInt64 时冲突，未施加 settings 的 2^53−1 上限。Bot 创建、凭据、版本变更及公共 bot.upsert 追加共用同一事务；触发器与延迟外键故障测试覆盖语句失败和最终提交失败回滚。公共 Sequence 与实体版本分离，未改变 epoch 或历史变化外键。
5. 并发与恢复：CAS 竞争只有一次成功；并发创建的 change_seq 唯一且按持久化排序单调；重开数据库 epoch、公开元数据和两种摘要认证保持。公共 changes 包另覆盖独立 Store 全局序号竞争。
6. 迁移：仅新增 0004，具有实体版本、能力及摘要类型/长度约束。storage 夹具以真实迁移集合推导下一版本，保留 checksum/name/future/gap 拒绝、锁竞争、失败升级全回滚、持久化台账与旧二进制拒绝断言；新增真实 0003→0004 升级覆盖管理员代次和 epoch 保持。未弱化原断言或修改 storage 实现。
