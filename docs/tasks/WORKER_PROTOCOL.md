# 子 agent 工作、审计与交接协议

## 1. 通用任务边界

每次只接受一个明确任务 ID、角色、卡片和基线。先读根约定、相关章节/局部代码和前置摘要；不要默认读取全仓库或整个计划。所有新增技术约束必须能追溯到 PRD、C-01～C-05 或已冻结契约；重要变更上报总调度，再由用户确认。

卡片路径是规划职责，并不证明当前源码已存在。发现现有工程命名不同先报告等价映射，复用现有实现，不为了符合卡上文件名搬目录。Schema/迁移版本由对应任务串行分配；不同agent不能并发改共同契约或抢迁移编号。

本目录定义执行流程，不授权本轮开始编码；后续仅在总调度传达的用户授权范围内执行。不得自行发起用户可见新聊天、对外消息、真实发布、现网部署或额外子agent。

## 2. 角色

| 角色 | 输出 | 权限限制 |
| --- | --- | --- |
| 规划 agent | 上下文估算、拆卡、依赖/接口影响建议、补充卡 | 不替用户选择需求/架构/安全变更，不偷偷实现业务 |
| 开发/研究 agent | 单卡实现或固定版本研究、相关检查、独立提交和交接报告 | 只改卡内范围；状态台账只由调度更新 |
| 审计 agent | 固定SHA的独立审计报告及必要验证结果 | 代码只读，仅可写自己的报告；不边审边修，不标总任务done |
| 修复 agent | 针对已编号审计问题的最小修复、回归证据和新SHA | 不顺手扩功能；不能以调整测试掩盖缺陷 |
| 集成 agent | 精确实现组合入目标分支、相关检查、集成报告/台账快照提交 | 不做需求变更；冲突若需新业务设计则交修复/规划；代码变后重审 |

审计角色与该任务实现者必须不同。验证/研究任务也要审计证据真实性和范围；独立审计并不要求重跑所有昂贵真机矩阵，但必须检查环境和记录确实支持结论。

## 3. 上下文预算和退出点

默认输入包≤12k tokens，通常只读3～5个主要实现文件及相应测试。预计输入+工作区材料/工具结果+输出不超过当前模型上下文60%，至少25%留给结果交付；实际窗口较小时按更小限制。文件数和token为工作约束，不声称不同GPT模型都能一次完成。

派发包必须包含：单卡、角色、基线SHA、工作目录/分支、允许路径、相关文档章节、前置摘要、已冻结API、环境状态和必跑检查。若调度未提供基线、只给“实现P8全部”、依赖尚未集成或上下文超预算，先返回澄清/拆分请求，不自行扩大任务。

到预算退出点时写checkpoint：已完成目标、精确SHA或未提交文件、未跑检查、风险、下一子任务输入与步骤。不能靠长历史压缩继续整阶段；不能把checkpoint当作验收完成。无法确定窗口时按材料体积/职责评估，必要拆卡；不要编造精确token使用统计。

### 拆分请求模板

```yaml
task_id: P08-14
outcome: split_required
reason: 需要跨三个管理功能域，预计超出本轮局部上下文
completed: []
uncommitted_paths: []
proposed_children:
  - id: P08-14-S01
    objective: 仅实现全局配置页面
    depends_on: [P08-13, P06-08]
    write_scope: [android/feature/management/settings/]
  - id: P08-14-S02
    objective: 仅实现设备会话管理
    depends_on: [P08-14-S01]
    write_scope: [android/feature/management/devices/]
remaining: 失败管理与父卡收口由规划agent补齐，不遗失原验收
```

子卡必须有与初始卡等价的目标/范围/验收/上下文/交接字段；registry登记后才派发。父卡验收必须覆盖全部子卡结果，不能因为拆卡丢失任务。

## 4. 开发交付与 Git

开始前检查工作区归属/基线；默认同一工作树一个写入者。保留用户及其他任务未提交文件，不自动清理。不采用全仓库 stage；只提交本任务实际修改，Conventional Commits 中文描述可用。已有未跟踪文档不能因依赖它就一并提交。

实现时维护相关契约/注释/测试；受影响检查失败先修复。外部环境缺失不伪造通过，返回 blocked。代码可以阶段性提交，但任务未完成不得说done；审计必须针对最终相关提交范围。审计报告引用真实实现SHA；实施报告可随实现提交，但不要在提交内预写自身SHA，提交后在交接及registry记录。

### 结果交接模板

```yaml
task_id: P05-02
role: developer
outcome: implemented # implemented / blocked / needs_user / split_required
base_sha: <真实基线>
implementation_sha: <真实最终实现提交>
commit_range: <基线..实现>
worktree: <实际路径或当前工作区>
changed_paths: [<仅当前任务文件>]
summary: <不超过800中文字符>
checks:
  - command: <真实执行命令，不含密钥>
    environment: <版本/真机或模拟器/网络条件>
    result: pass # pass / fail / not_run
    evidence: docs/tasks/reports/P05-02-implementation.md
acceptance: {<卡内条目>: <pass/fail/not_run及证据定位>}
handoff_interfaces: <下一任务必须知道的接口/错误/版本，简述>
unresolved: []
requested_decisions: []
```

这只是格式示例，没有任何真实执行结果。研究的负面发现可写 `outcome: implemented` 表示已交付研究报告，但明确门槛 `blocked/needs_user`，不能把兼容性写成通过。

## 5. 独立审计

派生 ID 为 `<原任务>-A01`，重审 A02/A03。登记为 `registry.tasks` 的附加条目，增加 `kind: audit`、`parent_id`、精确实现SHA；依赖使用 `subject_id` 表达被审任务，不让尚未done的父任务成为强依赖造成死锁。原卡 dependencies 不改，审计触发条件是原卡review及固定SHA。附加条目的状态也走统一状态值，但审计自身done只表示报告已交付，总任务仍需集成。

审计输入：原卡、PRD相关章节/C-01～05、基线和实现SHA、变更路径、实现摘要与实际检查记录。审计agent自己读取差异和关联代码，优先验证最易出错的权限/事务/并发/恢复边界；不整仓漫游。

必查：

- 范围是否只覆盖单卡、有没有偷偷加入新需求或删功能。
- 关键行为是否与固定契约/状态机相符，是否遗漏失败分支和提交边界。
- 测试是否真实执行、能证明验收，是否用桩结果冒充外部真机/系统结果。
- 依赖SHA、变更路径与当前待集成提交是否一致；无凭据/正文/原始敏感日志入库。
- 重要中文注释和相关文档是否同步，是否存在必须补的回归。

报告：`reports/<原任务>-audit-01.md`。每条发现记录 `finding_id`、严重度、文件/行或证据、触发条件/影响、修复方向及复验方式。无问题也说明检查范围和未执行限制，不能只写“LGTM”。

```yaml
task_id: P05-02-A01
subject_id: P05-02
reviewed_base_sha: <真实SHA>
reviewed_implementation_sha: <真实SHA>
verdict: PASS # PASS / CHANGES_REQUIRED / BLOCKED
findings: []
checks: []
limitations: []
report: docs/tasks/reports/P05-02-audit-01.md
```

PASS不表示豁免必需但未运行的检查。只读审计代码，报告独立提交；一旦需要修代码，停止审计并交修复角色。

## 6. 修复和复审

修复 ID `<原任务>-F01`；每张修复卡只覆盖一组相关发现，继承原卡的范围/禁止事项，并列 finding_id。规划agent建立卡和台账建议，总调度登记，不能仅在聊天说“把所有问题修掉”。修复提交后重审精确新SHA，核对已修发现及必要非回归；问题关闭有证据，不由开发自己销单。

多次审计/修复无法收敛，汇总相同根因给规划agent重新拆分或提交用户决定，不能机械循环到上下文耗尽。

## 7. 集成与阶段验收

派生 ID `<原任务>-I01`，`kind: integration`、`subject_id`、审计报告/实现SHA固定。集成触发条件为原卡review且最终审计PASS；不把原卡done作为依赖，避免环。集成agent运行目标分支状态检查、精确变更集成、相关构建/测试并记录前后SHA。默认同一写工作树中的提交可已位于目标分支，仍需确认其精确范围与结果，不重复cherry-pick。

结果应含：原任务ID、实现SHA、审计证据、目标分支、集成前/后SHA、实际检查、冲突/修改及是否需要重审。若合并产生业务代码修改，新结果必须重审；报告/台账纯元数据提交可不重跑全项目测试。

P11/P12/P15 是跨任务验收，执行agent读取已有证据并只补组合验证。依赖全部done不等于阶段自动通过；缺真机、缺NAS、缺签名必须明确not_run并阻塞对应验收。通过后由总调度记录门槛；真实Release/推送/现网操作仍按用户授权，不由任务完成自动触发。

## 8. 阻塞报告

报告具体阻塞条件、已完成内容/文件、缺少的最小输入、可继续的独立任务以及是否涉及用户决定。凭据仅报告“需要某测试配置的安全加载方式”，不让用户把服务账号密钥复制到报告。

MP必须改核心、RelayShelf需要改服务端、Android需要改变既定后台架构时，提供源码/实测证据、可行选项/代价和推荐理由，交总调度询问用户；等待决定期间只暂停相关分支。普通文件命名、局部算法和已授权修复自行完成。
