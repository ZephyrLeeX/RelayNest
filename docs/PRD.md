# RelayNest + RelayShelf 原生 Android 客户端｜产品需求文档

> **版本**：v1.0  
> **日期**：2026-10-20  
> **状态**：首版功能范围已确认；关键技术方案需通过开发前验证  
> **适用范围**：RelayNest 服务端、管理界面、Android 客户端、MoviePilot 接入插件和 RelayShelf 移动端集成

## 1. 产品概述

开发一套面向个人自托管环境的轻量消息平台 **RelayNest**，统一接收 MoviePilot、NAS 监控及其他自建程序的通知，并支持 Android 用户与具备交互能力的应用双向通信。同一个原生 Android APK 还应提供现有 **RelayShelf** 的完整客户端功能。

**产品目标**

- 不依赖 Telegram 等第三方即时通信客户端，按 Bot 分别查看通知、消息与交互记录。
- 提供易于接入的 REST API、Long Polling 和标准 JSON Webhook，兼容单向告警与双向消息应用。
- 以服务端持久化、断线补偿、去重和重试提高消息可靠性；不要求秒级通知。
- 保持个人使用场景的简单部署与低维护成本。

**职责边界**

RelayNest **仅负责消息接入、认证隔离、保存、路由、投递和通用交互事件转发**，不解析业务命令、不调用业务工具、不执行远程操作，也不负责业务级权限审核、危险操作确认及执行审计。上述能力均由接入应用（如 MoviePilot 或 NAS Agent）自行提供。

RelayShelf 与 RelayNest 是两个独立后端；Android 客户端直接调用 RelayShelf 现有 API，不合并数据库、身份系统或文件存储。

## 2. 用户与系统组成

**用户范围**：仅个人管理员使用 RelayNest；不开放注册、群聊或多租户功能。RelayShelf 原有多用户和共享功能不因此删减。

| 组成 | 技术与职责 |
| --- | --- |
| Android App | Kotlin + Jetpack Compose；Bot 聊天/通知、Bot 管理、RelayShelf 完整原生客户端 |
| RelayNest 服务端 | Go 单体，SQLite WAL，负责消息、Bot、投递、同步与管理 API |
| Web 管理后台 | 由 RelayNest 提供；只管理 Bot、凭据、连接和系统配置，**不查看历史、不聊天** |
| MoviePilot 插件 | 对接 MoviePilot V3 `3.1.5` 自定义通知配置，适配通知、回复及入站消息 |
| 其他接入应用 | NAS 监控、脚本和其他服务，按所需能力接入各自 Bot |
| RelayShelf 服务端 | 保持现有独立 Go + PostgreSQL 服务与业务接口，不因本项目迁移或重构 |

每个应用/服务默认使用**独立 Bot**，对应独立凭据、对话历史和通知配置；必要时同一服务可以建立多个 Bot。只发送告警的 Bot 不必支持交互。

## 3. RelayNest 功能需求

### 3.1 Bot 管理与安全

Android App 和 Web 后台均应支持：

- 创建、查看、编辑、启用、停用及永久删除 Bot，查看连接状态。
- 为每个 Bot 管理两套相互独立的凭据：**Bot API Token**（按发送/接收能力授权）和**仅可发送的入站 Webhook 密钥**。
- 分别重置两种凭据；旧凭据立即失效，不清除消息和未完成投递记录。
- 管理员会话独立于 Bot 凭据；Bot 只能访问自身授权范围，不能访问其他 Bot 或管理 API。
- 停用后暂停收发，保留配置、正常期限内历史及未完成投递；恢复启用后继续处理。
- 永久删除需二次确认，删除 Bot 的凭据、历史、待投递/失败消息和不再引用的附件。

### 3.2 消息与交互

首版支持：

- 纯文本、Markdown、图片、文件附件及普通链接。
- 回复引用与独立的会话消息记录。
- 结构化交互按钮（URL 或回调数据）；按钮回调原样交由接入应用处理。
- 消息编辑及跨设备变更同步。
- Android 主动发消息、Bot 返回回复；单向 Bot 仅展示通知。

**不要求首版支持发送方撤回消息。** 消息 ID、引用关系、编辑版本等应支持可靠同步，但具体 JSON 字段以另行制定的 API 规范为准。

### 3.3 消息投递可靠性

- **持久化成功才确认接收**：收到应用或 Android 消息后，服务端先成功提交 SQLite 再回复成功。
- **至少一次投递**：接入应用通过 Long Polling 获取待处理消息，再独立提交 ACK；取到消息不视为已确认。
- **幂等与重试**：提供稳定消息 ID/幂等机制；网络超时或未 ACK 时可重试，避免重复生成消息。
- **失败保留**：超过自动重试阈值后转入失败队列，允许管理员手动重试；消息与关联附件不被普通历史清理误删。
- **严格区分状态**：消息已持久化、接收方已 ACK、用户已读、业务执行成功是不同概念。业务幂等和实际执行结果由接入应用负责。

具体 ACK 超时、重试间隔、最大次数和租约参数在技术设计中确定。

### 3.4 历史记录和数据清理

- 所有 Bot 使用统一的**全局历史保留期限，默认 30 天**，管理员可修改。
- 保留期限只接受正整数天；不支持 0，0 不表示立即清理、禁用或无限保留。不新增业务性上限；安全计算和存储的技术边界由契约明确并独立审计。
- 已完成投递的普通聊天和通知历史按期限自动清理；关联且不再被引用的附件一并清理。
- **未完成投递、未 ACK 和失败队列中的消息及附件受到保护**，不按普通期限删除。
- 任一 Android 设备长时间离线都不阻止历史清理。恢复连接时只同步服务器仍保留的数据；发现历史缺口应向用户提示。
- 管理员明确永久删除 Bot 时，可取消并删除其受保护队列；此操作不属于普通自动清理。

### 3.5 接入协议

| 协议 | 方向及用途 |
| --- | --- |
| HTTP REST API | 接入应用发送/编辑消息，上传附件，以及其他标准消息操作 |
| Long Polling + ACK | 接入应用主动领取 Android 发来的消息并确认处理接收 |
| 入站 Webhook | 外部监控系统向指定 Bot 发送通知；**仅接受 RelayNest 标准 JSON** |
| Android WebSocket | App 前台接收新消息/变更提示，结合增量同步补齐记录 |

- API 使用相应 Bot Token；Webhook 使用独立仅发送密钥。
- Webhook 不提供第三方专有 JSON 字段映射、转换模板或脚本执行。不支持标准 JSON 的程序需自行适配。
- 首版**不提供出站 Webhook**；外部接入应用使用 Long Polling 收取消息。
- 所有接口需处理鉴权失败、请求验证、消息幂等与明确错误响应；字段、端点和错误码待 API 规范定义。

### 3.6 附件

- 图片和文件上传后保存在 RelayNest 的**独立持久化目录**；SQLite 仅保存元数据、关联关系和投递状态，不存文件二进制。
- 默认单张图片上限 **10 MiB**、普通文件上限 **50 MiB**，均可通过全局配置调整。
- 附件上限只接受正整数字节；不支持 0，0 不表示立即清理、禁用或无限大小。不新增业务性上限；安全计算和存储的技术边界由契约明确并独立审计。
- 外部图片/文件 URL 作为普通链接，不自动抓取为持久化附件。
- 附件按权限下载；清理历史时不得删除仍被其他消息或未完成投递引用的文件。

## 4. Android 客户端需求

### 4.1 Bot 对话与管理

- 展示按 Bot 分离的会话列表、历史消息、未读数、消息状态与附件。
- 支持发送消息、回复引用、点击交互按钮、Markdown/图片预览、文件下载和消息编辑更新展示。
- 提供与 Web 后台一致的 Bot 管理能力；不要求 Web 端提供聊天功能。
- 本地可缓存已同步内容，网络恢复时根据同步游标增量补齐；识别消息重复和历史清理缺口。

### 4.2 多设备

- 允许 Android 手机、平板等设备同时登录同一账号。
- 消息历史和每个 Bot 的**已读状态在设备间同步**。
- 登录会话、同步游标、本地缓存、FCM 注册和通知偏好**按设备独立**。
- 支持单设备退出及远程撤销指定设备会话，不影响其他设备登录。

### 4.3 后台通知

- App 前台使用 WebSocket；后台优先使用 FCM 提醒，利用 WorkManager 在系统允许时定期同步；每次打开 App 立即补偿同步。
- FCM **仅用于提醒或唤醒**，不是消息的权威存储；FCM 不可用、设备离线或系统禁止通知时，仍可在再次连接后同步服务器现存消息。
- 提供全局通知开关、按 Bot 开关、免打扰时段及锁屏内容预览设置；各设备独立配置。
- 按消息 ID 去重提醒，并与共享已读状态联动；尊重 Android 系统通知权限与免打扰设置。
- 首版不实现常驻 Android 前台服务；不保证 FCM 或 WorkManager 在锁屏状态下精确准时运行。

### 4.4 统一登录与双后端会话

- App 提供**一个账号密码输入界面**，分别向 RelayNest 和 RelayShelf 登录，各自保管会话；这不是服务端 SSO。
- 用户手动维护两个后端的相同用户名和密码；系统**不自动同步密码**或联动改密。
- RelayShelf 要求 TOTP 时，必须按其现有挑战流程继续验证，不得跳过。
- 支持某一后端登录成功、另一后端失败的部分登录状态，并可单独重新认证失效的一端。
- 保留两端独立的登录恢复、过期处理和注销流程；会话凭据安全保存，不长期明文保存用户密码。
- 必须实际验证 Android 原生 HTTP 客户端对 RelayShelf Cookie、CSRF、Origin/Referer 的兼容性。

## 5. RelayShelf 原生客户端范围

**首个正式版本应完整覆盖当前 RelayShelf 的现有产品功能。** 以原生 Kotlin/Compose 界面直接访问既有 API，不以 WebView 替代业务功能，不未经确认修改服务端。

| 功能域 | 必须覆盖的能力 |
| --- | --- |
| 账号与安全 | 登录、TOTP、会话/设备管理、注销、权限和异常处理 |
| 内容管理 | 文本、Markdown、代码、链接、图片、文件的创建、浏览、详情、编辑、删除与恢复 |
| 内容生命周期 | Temporary/Permanent、过期、回收站及既有生命周期规则 |
| 文件传输 | 分片上传、断点续传、校验与去重、下载、失败恢复、预览 |
| 检索与整理 | 搜索、过滤、标签、收藏 |
| 分享与协作 | RelayShelf 已有的跨用户发送、转发、共享等功能 |
| 实时与隐私 | SSE 更新、敏感内容处理和异常恢复 |

验收时应根据实际部署版本的 OpenAPI 和现有界面建立逐功能核对表。若发现现有 API 不足，先提出缺口和影响，不自动变更 RelayShelf 服务端。

## 6. MoviePilot 首个集成

- 接入版本基线：**MoviePilot V3 `3.1.5`**。
- 采用 MoviePilot「通知 → 添加 → 自定义」配置，配合**专用 V3 插件**完成消息转换和转发，优先不修改 MoviePilot 主程序。
- 插件通过 RelayNest HTTP API 发送主动通知和业务回复，通过 Long Polling 获取 Android 用户输入；命令识别、业务执行、业务安全确认及结果生成继续由 MoviePilot 自行完成。
- 应覆盖主动通知、双向文字回复、搜索候选列表、按钮回调、引用上下文与必要的图片/附件；不同通知分发路径不得出现遗漏或重复。

**集成风险（尚未验证）**：MoviePilot `NotificationChannel` 使用固定枚举，自定义通知配置并不自动成为完整消息渠道；按钮回调还受渠道能力限制。开发前须用最小插件 PoC 验证**自定义配置保存 → 主动通知 → 文本入站 → 定向回复 → 按钮回调**完整链路。如果必须修改 MoviePilot 主程序，应先报告兼容性缺口，不得擅自扩大改动。

## 7. 部署与非功能需求

| 项目 | 需求 |
| --- | --- |
| 部署 | 飞牛 fnOS Docker Compose；Go 单应用容器，内嵌轻量 Web 管理页面 |
| 内部网络 | RelayNest 提供内网 HTTP/WebSocket，不直接将明文服务端口暴露公网 |
| 公网接入 | 由 **OpenWrt Nginx** 统一负责 HTTPS/TLS 终止、反向代理与 WebSocket 转发；支持自定义公网端口 |
| 数据持久化 | SQLite WAL 与附件目录均使用宿主机持久化挂载，重启和正常更新不清空数据 |
| 备份 | **SQLite 完全不自动备份**；不要求异地备份、自动恢复，接受故障时可能永久丢失历史 |
| 监控 | 基础健康检查、连接状态、失败队列状态和错误日志；不建设复杂独立监控平台 |
| 安全 | 管理员会话和 Bot 凭据隔离、HTTPS 外部访问、凭据不写入普通日志、请求大小限制、基本登录防护 |
| 构建发布 | GitHub Actions 构建 APK 和 Docker 镜像，支持正常更新部署 |

Nginx 需正确处理 WebSocket 升级、Long Polling 超时和附件上传大小限制。RelayNest 的消息投递保障不等于对磁盘损坏、误删除或普通历史到期清理提供永久恢复承诺。

## 8. 验收标准

| 编号 | 验收项 | 通过条件 |
| --- | --- | --- |
| AC-01 | Bot 管理 | Android 与 Web 均可创建、停用、恢复、删除 Bot，并管理独立凭据 |
| AC-02 | 访问隔离 | Bot API 与 Webhook 各按权限访问本 Bot；重置凭据后旧凭据不可继续使用 |
| AC-03 | 消息与附件 | 约定消息类型、按钮回调、编辑及附件上传下载可用 |
| AC-04 | 可靠投递 | 落库后回执；Long Polling + ACK + 重试 + 去重；失败队列可手动重试 |
| AC-05 | 30 天清理 | 全局保留期限生效；未完成投递/失败消息及附件未被误删 |
| AC-06 | 标准 Webhook | 接受合法标准 JSON，拒绝无权限请求及不符合协议的载荷 |
| AC-07 | MoviePilot | 主动通知、文本命令、正确会话回复和候选交互通过 V3 插件端到端测试 |
| AC-08 | Android 多设备 | 同时在线、共享历史和已读、独立会话/通知、单设备会话撤销可用 |
| AC-09 | Android 后台 | FCM 真机测试完成；定期和打开时补偿同步正确，不因推送失败丢失服务器消息 |
| AC-10 | 登录与 TOTP | 统一登录入口，两后端独立会话，RelayShelf TOTP 与部分登录状态正确 |
| AC-11 | RelayShelf 原生覆盖 | 依据现有功能矩阵逐项验证，不能以 WebView 或无说明的删减代替 |
| AC-12 | 部署 | fnOS Compose 重启/更新不丢持久化数据；OpenWrt Nginx HTTPS、WS、附件传输正常 |

## 9. 开发前必须验证的技术事项

这些是**验证任务，不是新增产品需求**：

1. **MoviePilot 插件 PoC**：确认自定义渠道与 V3 固定渠道枚举之间的兼容性，验证广播/定向回复和按钮回调。
2. **RelayShelf Android API PoC**：验证登录/TOTP/Cookie/CSRF、分片上传下载、SSE 断线恢复，并核对已部署版本的功能矩阵。
3. **FCM 真机 PoC**：在目标 Android 设备上验证前后台、锁屏、Wi-Fi/蜂窝切换、权限拒绝与重启后的补偿同步。
4. **消息模型设计**：另行定义正式 API Schema、消息状态/编辑事件、去重键、ACK 时机与重试参数；不得把演示数据当作已冻结接口合同。

## 10. 首版范围以外

不开发 Telegram Bot API 兼容、通用聊天/群聊、网页版消息历史或聊天、RelayNest 业务命令解析与 MCP 工具执行、出站 Webhook、第三方 Webhook 字段映射、发送方撤回消息、复杂多用户权限体系、SQLite 自动备份与容灾系统，以及默认常驻 Android 前台服务。

---

**需求使用说明**：本文是首版产品需求与验收基线，不是 API 字段规格或数据库设计。已列出的技术风险必须验证；实现者不能擅自删除 RelayShelf 原有功能、把业务执行放进 RelayNest，或把尚未验证的 MoviePilot / Android 兼容性描述成已完成。
